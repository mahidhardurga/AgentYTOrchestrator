Requirement 1 · Content writing agent · Platform decision

Claude Managed Agents or Amazon Bedrock

The best solution for each path, compared factor by factor, with a verdict and the guardrails needed because the agent will act for a VP.

Verdict

Choose Claude Managed Agents, with approval, publishing and secrets running in our own AWS account.

It gets us to a working pilot in about 10 working days against about 19 for Bedrock, with fewer parts to maintain. It has the two features this job needs and Bedrock lacks: built-in web research and a grader that scores drafts against a rubric. Monthly run cost is about the same on both, so people time and risk decide.

The score is close: 3.7 for Managed Agents and 3.5 for Bedrock out of 5. Managed Agents wins on speed, fit and upkeep. Bedrock wins on security controls, data handling and maturity. Which one comes out ahead depends on what the company values most.

Pick Bedrock instead if any one of these is a hard rule:

  • Prompts and outputs must stay inside our AWS boundary, including private network only.
  • A new outside data processor cannot be approved in time.
  • Beta services are not allowed in production.
  • A managed content policy engine (Bedrock Guardrails) is mandated.

If AWS billing and IAM are required but a beta service is acceptable, use Claude Platform on AWS. It is operated by Anthropic, exposes the same API including Managed Agents, and signs in with AWS IAM and bills through AWS Marketplace. Treat it as a variant of Path A.

Most important guardrail

The agent never holds or sees the VP's credentials, and the VP never shares a password. The VP grants LinkedIn access once through LinkedIn's own consent screen, and nothing is posted without the VP's or a named delegate's approval of the exact text. Details in Executive identity.

The options

Path A

Claude Managed Agents

Anthropic runs the agent loop, sandbox, schedule, grader and memory. We run a small service for approval, publishing and state.

Path A2

Managed Agents via Claude Platform on AWS

Same as A, reached through AWS IAM and billed through AWS Marketplace. Anthropic still operates it.

Path B

Amazon Bedrock

AWS runs the model. We build the workflow, research tools, grader, memory and scheduling from AWS services.

Why this is not a like-for-like choice

According to Anthropic's platform availability matrix, Managed Agents, the built-in web search and web fetch tools, code execution, the Files API and Message Batches are not offered through Bedrock. Bedrock does support tool use, prompt caching, structured outputs, thinking and citations. So on Bedrock we build the pieces that Managed Agents provides, and we get AWS's security and compliance tooling in return.

Guardrails for acting as the VP

Content posted from a VP's profile speaks for the VP and the company. The rules below apply on either path.

Do not use the VP's own logins

Using the VP's personal Claude, AWS or LinkedIn login or password is the wrong shortcut. Actions are attributed to the VP personally, secrets spread across laptops and chat, access outlives the project, MFA is bypassed, and the VP cannot take access back without losing their own. Use delegated access instead.

LinkedIn's access tokens last about 60 days, and refresh tokens are limited to approved programs, so plan a recurring re-consent. LinkedIn's API terms likely forbid credential sharing and unofficial automation, so use only the official posting API and have legal confirm.

2. Approval and authority

  • Written delegation. The VP confirms in writing who may approve on their behalf, and the allow-list of approver IDs is enforced in code.
  • Approval is bound to the exact text. Approving draft 2 stores a hash of that text. Any edit voids the approval, and only the approved hash can be published.
  • Approvals expire after 24 hours and are recorded with who approved, when and the hash.
  • Hard limits in code: at most two posts a week, a fixed posting window, and no publishing from a failed or unchecked run.
  • Kill switch. One flag pauses everything, and the approver can also reply "pause" to the bot.
  • Dry-run mode. For the first 2 to 4 weeks drafts go to the VP, who posts manually. Nothing auto-posts.

3. Content policy

  • Banned topics list approved by comms and legal: unreleased products, customers and deals, financials and forward-looking statements, M&A, legal and HR matters, politics, and anything that could be material non-public information.
  • Every factual claim needs a source and a verbatim quote, checked by our code before the approver sees it.
  • Pattern checks for secrets, personal data and internal names before sending a draft.
  • Short quotes only, with a similarity check against the source so nothing is copied.
  • A decision on whether posts disclose AI assistance, aligned with company policy.

4. Team access and audit

  • Four roles: Developer, Operator, Publisher and Approver. The role that can publish cannot edit code, and developers cannot read the LinkedIn secret.
  • Separate dev and prod, MFA for everyone, and access reviewed monthly.
  • Log every run, draft, approval and publish with IDs. Keep logs in write-once storage for the retention period the company requires.
  • Alert on any post outside the window, an approval from an unknown ID, any secret read outside the publisher, and spend spikes.
  • Incident steps written in advance: delete the post, revoke the LinkedIn authorization, pause the schedule, then review.

5. Sign-off before launch

Security review, legal and comms approval of the content policy, vendor review of the model provider, and the VP's written delegation. Name an owner and a backup, and review a sample of posts monthly.

Repository note

This repository currently tracks client_secret.json in git. That must be removed and rotated before any executive credentials are involved, and no secret should ever sit in a .env file on a laptop for this project.
