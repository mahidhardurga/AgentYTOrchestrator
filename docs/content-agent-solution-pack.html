Requirement 1 · Content writing agent

Content writing agent on Claude: explainer, solution design and platform decision

Everything in one place. Part 1 explains Claude Managed Agents in plain language. Part 2 is the solution design. Part 3 compares Managed Agents with Amazon Bedrock, gives a verdict, and sets guardrails for acting as a VP.

Part 1 · The explainerNo prior knowledge needed.

What are Claude Managed Agents?

An AI agent is Claude working through a job in several steps. It reads, searches, writes files, checks its own work, and keeps going until it is done. Normally you have to build the machinery around that: a loop that calls the model, a safe computer where its commands run, somewhere to keep its files, and a way to watch it.

Claude Managed Agents is Anthropic's hosted version of that machinery. You describe the agent once (which model, what instructions, which tools). Anthropic runs the loop and gives each run its own sandboxed computer. You start a run, watch what it does, and collect the files it produces.

Plain analogy

Building your own agent is like setting up an office, buying a laptop and hiring a person. Managed Agents is hiring a remote contractor who arrives with their own laptop and a written job description. You hand over a task and get the finished work back.

It launched in public beta in April 2026, so details can still change. Every call carries a beta header (the official SDK adds it for you).

The four pieces

Everything in Managed Agents comes down to four things. Learn these and the rest of the docs read easily.

/v1/agents

Agent

The job description. Model, system prompt, tools, skills. Saved and versioned. You create it once and reuse it.

/v1/environments

Environment

The template for the computer. Which packages are installed and which websites it may reach.

/v1/sessions

Session

One run. It pairs an agent with an environment and a first instruction, then keeps its own conversation and files.

event stream

Events

Everything that happens in a session, as a live feed: your messages, the agent's replies, each tool call, status changes.

How one run goes

Create the agent (once)
Model, instructions and tools are saved. You keep the agent ID. Editing the agent later creates a new version, and old runs keep the version they started with.
Create the environment (once)
Choose networking. limited blocks everything except the sites you list. unrestricted allows all.
Start a session
Reference the agent and environment. Optionally attach files, a GitHub repo or a memory store, and set a spending cap.
Send a task and watch events
You send a user.message. The agent works, and the stream shows each step. The session goes running, then idle when it needs you or is finished.
Collect the outputs
Files the agent saves in /mnt/session/outputs/ can be downloaded through the Files API.

A container is the sandboxed computer where the agent's commands and file edits actually run. The thinking happens on Anthropic's side and acts on the container through tools.

What can an agent do?

Agents act through tools. There are three kinds.

KindExamplesWho runs it
Built-in toolsetbash, read, write, edit, glob, grep, web_search, web_fetchAnthropic, in the session's container (web tools run on Anthropic's servers)
MCP serversConnections to outside services such as GitHub or AsanaAnthropic's orchestration layer, using credentials you store in a vault
Custom tools"Post to LinkedIn", "look up this customer"You. The agent asks, your code answers

Permissions

Each tool has a policy. always_allow runs it. always_ask pauses the session until your code approves or denies. auto lets the server judge each call: run it, deny it as high-risk, or pause for you. Anything that publishes or spends money should stay behind a person.

Good habit

A bare toolset turns on all eight tools, web search and fetch included. Switch off what the job does not need and list the sites it may read.

Features that matter for real work

Memory stores

Sessions forget everything when they end. A memory store is a folder of small text files that persists across runs, so the agent can remember which topics it already used.

Outcomes

You write a rubric. A separate grader scores the agent's work against it and sends back what is missing, until it passes or hits a retry limit. Good for "keep going until it is right".

Scheduled deployments

A cron schedule that starts a session on its own, such as every Tuesday and Thursday morning. Each firing is logged as a run.

Vaults

Safe storage for API keys and OAuth tokens. They are filled in when the agent makes a request, so the sandbox never holds the real secret.

Session budgets

A hard dollar cap on one session. At the cap it pauses instead of running on.

Multi-agent and skills

An agent can hand parts of a job to helper agents. Skills are reusable instruction packs, such as a house style guide.

Some of these were gated behind an access request early in the beta. Confirm your account has outcomes and memory stores before relying on them (this is Phase 1 of the plan).

Part 2 · Solution design: Content writing agent on Claude Managed AgentsDraft for lead review. Topics are deliberately left open and plug in later (see Topics).

Summary for review

What we are building. An agent that, twice a week, finds a timely topic inside a brief we give it, researches it with sources, writes three LinkedIn drafts in the owner's voice, and checks them against a quality rubric. A person approves one on their phone, and only then is it posted.

The shape. Anthropic hosts the thinking and the sandbox. We host one small service that handles everything with side effects: approval messages, source checks, publishing and state. The agent can read the web and write drafts. It cannot post, and it holds no credentials.

Built on

Scheduled deployment, session with outcome and grader, memory store for voice and history, limited-network sandbox.

Our code

One small webhook service, a state table, a claims checker, an approval channel adapter, a publisher adapter.

Effort

About 10 working days to a working pilot, then a 2-week shadow period where nothing posts without review.

Run cost

Roughly $0.50 to $1.50 per approved post. Under $10 a month at two posts a week (estimate, to be measured).

Decisions needed from the lead

Six, all in the last section with a recommended default each: approval channel, publish method, model, topic mode, who owns the LinkedIn app, and monthly budget cap.

Why Managed Agents, and what it does not remove

The Medium article is a good reference for the pipeline: pick a topic, research, draft three, score, approve by message, post. Its author runs it as a script on a timer. We keep that pipeline and change how it runs.

OptionWhat we would hostFit
Script on a timer (the article)Cron, the model loop, search, scoring loop, stateCheapest to start. We own every moving part and the scoring loop is hand-built.
Agent SDK on a serverThe runtime, the sandbox, a schedulerGood for coding agents. More to operate than this job needs.
Managed AgentsOne small webhook serviceScheduling, sandbox, grader loop, memory and versioning come from the platform.

What Managed Agents gives us here. The schedule and run log come from deployments. The draft, grade and revise loop comes from outcomes, with the grader in a separate context so it does not mark its own homework. Voice samples and the posting history live in a memory store that a person can edit. Every agent edit is a new version we can pin or roll back.

What it does not remove. We still need a small always-on endpoint for webhooks, a place to keep state, and the code that talks to the approval channel and LinkedIn. It is also in beta and Claude-only. A plain script would be cheaper for a pipeline this linear, so the case for Managed Agents rests on less to operate and on the grader and memory features, and we should review that after the pilot.

One run, step by step

The deployment fires
Tuesday and Thursday at the chosen time. Start can drift a few minutes, so drafting happens well before the intended posting time.
The agent reads its memory
Voice guide, sample posts, topic brief, last 60 days of topics, and the reviewer's past edits.
It finds and researches a topic
Searches the allowed sites, shortlists five, picks one that fits the brief and has not been used. Saves quotes and URLs to sources.json.
It writes three drafts and the grader scores them
Three different hooks. The independent grader checks each rubric criterion and sends back gaps until it passes or hits the retry limit.
The session goes idle and our webhook fires

A person approves
Drafts and sources go to the approver. They reply with a pick, a revision note, or skip.
Revisions go back into the same session

Approved text is published, then recorded
The publisher posts it. The orchestrator writes the topic and the reviewer's edits to the memory store so the next run starts better.

Components in detail

The writer agent

  • Model: Claude Sonnet 5.5 to start. It is a one-field change to try Opus 5.5 during the pilot.
  • Tools: file read and write, glob, grep, bash (for counting characters and checking today's date), web search and web fetch limited to the allowed sites. No publishing tool, no outside MCP servers.
  • Network: limited. Only the allowed news sites are reachable. The sandbox holds no secrets.
  • Prompt: short and stable. Role, output files and format, and "read the memory store first". The voice and rules live in memory files so a person can change them without touching the agent.
  • Later option: a cheaper Haiku 5.5 research helper for reading-heavy topics. Add it only if measurements show the main agent is spending most of its tokens reading.

The outcome and grader

The kickoff event is an outcome whose deliverable is the drafts file. The grader runs in its own context and has no web access, so it judges form and voice and checks that each claim points to a quote in sources.json. Whether the quote is real is checked afterwards by our code.

Starter rubric (tuned during the pilot):

  • Three drafts that differ in hook and structure.
  • Each is 900 to 1,300 characters, with an opening line under 140 characters that makes a specific claim.
  • Each factual claim maps to an entry in sources.json with a URL and a verbatim quote.
  • No phrases from the banned list. Sentence length, person and formality match the voice guide.
  • One concrete example, number or story per draft.
  • Ends with one question or one takeaway, never both.
  • The topic is not in the last 60 days of history.

Memory store layout

/voice/style-guide.md          tone, structure, do and don't
/voice/samples/01.md ...       15-20 of the owner's best posts
/brief/topics.md               what to write about (supplied by the lead)
/brief/angles.md               points of view and no-go areas
/history/topics.md             every topic used, with date and result
/feedback/YYYY-MM-DD.md        what the reviewer changed and why

Mounted read-only so the agent cannot rewrite its own history. The orchestrator is the only writer, through the memory API. Memory files are limited to 100KB each, so many small files is the right shape. Nothing secret is ever stored there.

Orchestrator service

  • A small HTTPS app on any serverless host, with two endpoints: one for Anthropic webhooks, one for the approval channel.
  • Webhooks are registered in the Anthropic Console and are signed. The SDK verifies the signature.
  • The idle webhook also fires when a session is waiting on a tool approval or has hit its budget, so the handler checks the stop reason before treating it as "drafts ready".
  • Webhooks can arrive twice, out of order, or be dropped after three failed attempts. So handlers dedupe on event ID, read state from the session, and a sweeper job every 15 minutes lists recent runs and picks up anything missed.
# on session.status_idled  (sketch, confirm field names in Phase 1)
session = client.beta.sessions.retrieve(event.data.id)
stop = latest_idle_stop_reason(client, session.id)   # list events, read newest idle
if stop == "end_turn":
    files = client.beta.files.list(scope_id=session.id,
                                   betas=["managed-agents-2026-04-01"])
    drafts, sources = load(files)
    report = check_claims(sources)                   # plain code, no model call
    send_for_approval(drafts, sources, report)       # Telegram or WhatsApp adapter
    state.set(session.id, "awaiting_approval")
elif stop == "budget_reached":
    alert_owner(session.id)

# on approver reply "revise 2: shorter and less formal"
client.beta.sessions.events.send(
    session_id=sid,
    events=[{"type": "user.message",

)

Claims checker (no model)

For each entry in sources.json it confirms the URL is on an allowed site, fetches the page, and confirms the quoted text appears. Drafts with a failed claim go to the approver flagged, with the failing claim shown. This catches invented sources without paying for a second model call.

Approval channel

A thin adapter with three actions: pick a draft, request a revision, skip. Recommended default is a Telegram bot, because it supports buttons and has no template rules. The repo already sends review messages over WhatsApp with Twilio. The Twilio sandbox needs the recipient to re-join periodically, and messages we start outside a 24-hour reply window need approved templates, so confirm those rules with Twilio before choosing it for a twice-weekly job.

Publisher

Two implementations behind one interface. Manual: the final text is sent to the owner to paste into LinkedIn. API: the orchestrator posts through LinkedIn's posting API using a member token. Ship Manual first so the agent is useful before API access is approved. LinkedIn access tokens are short-lived (about 60 days at the time of writing), so the API publisher needs an expiry alert. Check LinkedIn's current API terms and token rules when building. Posting to a company page needs an additional LinkedIn approval.

Agent definition as files

Keep the agent, environment and deployment as version-controlled files in the repo and sync them with the ant CLI, so the control plane is reviewed like code. The orchestrator uses the SDK for runtime calls only.

Topics: kept open on purpose

Nothing in the design depends on the subject area. The brief is a file in the memory store, so changing focus means editing a file and not rebuilding anything. Three modes are supported:

ModeHow it worksBest for
DiscoverThe agent searches the allowed sites and picks a topic that fits the briefTimely, news-driven posts
AssignedWe start a session with a specific topic and angleProduct launches, events, requests
BacklogThe agent works through a queue of ideas in the briefEvergreen series

What we need when the topics are decided:

  • The focus areas and the audience.
  • The point of view or angle we want to be known for, and topics to avoid.
  • 5 to 10 sites the agent may read.
  • 15 to 20 past posts we like, and any banned phrases.

Safety and control

  • Human approval on every post. There is no path from the agent to LinkedIn that skips a person.
  • No secrets in the sandbox. Posting and approval credentials stay in the orchestrator's secret store. This design needs no vault.
  • Web content is untrusted. Only allowed sites are readable, the agent cannot act on the outside world, and the claims checker plus the human see every source.
  • Spend caps. A budget on each scheduled run, a retry limit on the outcome, and an alert when a run pauses at its cap.
  • Pinned versions. The deployment pins an agent version, so a prompt change goes live only when we choose.
  • Audit trail. Every session has a viewable trace in the Anthropic Console, and every memory change is versioned.

Part 3 · Platform decision: Claude Managed Agents or Amazon BedrockThe best solution for each path, a side-by-side comparison, a verdict and guardrails for acting as a VP.
Verdict

Choose Claude Managed Agents, with approval, publishing and secrets running in our own AWS account.

It gets us to a working pilot in about 10 working days against about 19 for Bedrock, with fewer parts to maintain. It has the two features this job needs and Bedrock lacks: built-in web research and a grader that scores drafts against a rubric. Monthly run cost is about the same on both, so people time and risk decide.

The score is close: 3.7 for Managed Agents and 3.5 for Bedrock out of 5. Managed Agents wins on speed, fit and upkeep. Bedrock wins on security controls, data handling and maturity. Which one comes out ahead depends on what the company values most.

Pick Bedrock instead if any one of these is a hard rule:

  • Prompts and outputs must stay inside our AWS boundary, including private network only.
  • A new outside data processor cannot be approved in time.
  • Beta services are not allowed in production.
  • A managed content policy engine (Bedrock Guardrails) is mandated.

If AWS billing and IAM are required but a beta service is acceptable, use Claude Platform on AWS. It is operated by Anthropic, exposes the same API including Managed Agents, and signs in with AWS IAM and bills through AWS Marketplace. Treat it as a variant of Path A.

Most important guardrail

The agent never holds or sees the VP's credentials, and the VP never shares a password. The VP grants LinkedIn access once through LinkedIn's own consent screen, and nothing is posted without the VP's or a named delegate's approval of the exact text. Details in Executive identity.

The options

Path A

Claude Managed Agents

Anthropic runs the agent loop, sandbox, schedule, grader and memory. We run a small service for approval, publishing and state.

Path A2

Managed Agents via Claude Platform on AWS

Same as A, reached through AWS IAM and billed through AWS Marketplace. Anthropic still operates it.

Path B

Amazon Bedrock

AWS runs the model. We build the workflow, research tools, grader, memory and scheduling from AWS services.

Why this is not a like-for-like choice

According to Anthropic's platform availability matrix, Managed Agents, the built-in web search and web fetch tools, code execution, the Files API and Message Batches are not offered through Bedrock. Bedrock does support tool use, prompt caching, structured outputs, thinking and citations. So on Bedrock we build the pieces that Managed Agents provides, and we get AWS's security and compliance tooling in return.

Guardrails for acting as the VP

Content posted from a VP's profile speaks for the VP and the company. The rules below apply on either path.

Do not use the VP's own logins

Using the VP's personal Claude, AWS or LinkedIn login or password is the wrong shortcut. Actions are attributed to the VP personally, secrets spread across laptops and chat, access outlives the project, MFA is bypassed, and the VP cannot take access back without losing their own. Use delegated access instead.

LinkedIn's access tokens last about 60 days, and refresh tokens are limited to approved programs, so plan a recurring re-consent. LinkedIn's API terms likely forbid credential sharing and unofficial automation, so use only the official posting API and have legal confirm.

2. Approval and authority

  • Written delegation. The VP confirms in writing who may approve on their behalf, and the allow-list of approver IDs is enforced in code.
  • Approval is bound to the exact text. Approving draft 2 stores a hash of that text. Any edit voids the approval, and only the approved hash can be published.
  • Approvals expire after 24 hours and are recorded with who approved, when and the hash.
  • Hard limits in code: at most two posts a week, a fixed posting window, and no publishing from a failed or unchecked run.
  • Kill switch. One flag pauses everything, and the approver can also reply "pause" to the bot.
  • Dry-run mode. For the first 2 to 4 weeks drafts go to the VP, who posts manually. Nothing auto-posts.

3. Content policy

  • Banned topics list approved by comms and legal: unreleased products, customers and deals, financials and forward-looking statements, M&A, legal and HR matters, politics, and anything that could be material non-public information.
  • Every factual claim needs a source and a verbatim quote, checked by our code before the approver sees it.
  • Pattern checks for secrets, personal data and internal names before sending a draft.
  • Short quotes only, with a similarity check against the source so nothing is copied.
  • A decision on whether posts disclose AI assistance, aligned with company policy.

4. Team access and audit

  • Four roles: Developer, Operator, Publisher and Approver. The role that can publish cannot edit code, and developers cannot read the LinkedIn secret.
  • Separate dev and prod, MFA for everyone, and access reviewed monthly.
  • Log every run, draft, approval and publish with IDs. Keep logs in write-once storage for the retention period the company requires.
  • Alert on any post outside the window, an approval from an unknown ID, any secret read outside the publisher, and spend spikes.
  • Incident steps written in advance: delete the post, revoke the LinkedIn authorization, pause the schedule, then review.

5. Sign-off before launch

Security review, legal and comms approval of the content policy, vendor review of the model provider, and the VP's written delegation. Name an owner and a backup, and review a sample of posts monthly.

This repository currently tracks client_secret.json in git. That must be removed and rotated before any executive credentials are involved, and no secret should ever sit in a .env file on a laptop for this project.
