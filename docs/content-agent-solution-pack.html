Content writing agent on Claude Managed Agents: how it works and how to build it

A simple guide with scenarios, diagrams and a complete step-by-step implementation plan.

Part 1 · UnderstandWhat we are building and how Managed Agents fits.

In 30 seconds

We are building an AI writing helper. On a schedule it picks a topic from a list we give it, researches trusted sources, writes three drafts in our style, and checks its own work. A person reviews and approves. Only then does the text go to wherever we decide: an internal channel, a wiki, an email, or somewhere public later.

We build it on Claude Managed Agents. Anthropic hosts the workplace where the agent runs. We add one small service for review and delivery.

About 10 working days

To a working pilot, followed by a 2-week trial where every item is reviewed.

About $7 to $15 a month

To run at two items a week. Waiting for a reviewer costs nothing.

A person always approves

Nothing is delivered without a named approver signing off on the exact text.

Easy to change

Topics, style and destination are files and settings, not rebuilds.

Two things to know

Early release. Managed Agents is in beta, so we pin versions, test every change, and keep our own parts small and swappable.

Data. Work in the agent is handled by Anthropic's service. For the pilot we use public or low-sensitivity sources only. Confidential material needs a security review first.

Claude Managed Agents, simply

Think of renting a furnished office with a smart assistant already inside.

We describe the assistant's job once. Anthropic provides everything around it: a safe workspace, a clock for schedules, a notebook that remembers, and a second reviewer that checks work against a checklist. We only add the parts that touch our own systems.

Part 3 · Implementation planThe full plan: prerequisites, 12 steps, and how to run it.

Before you start

Gather these first. Most delays come from waiting on access and approvals, so ask for them on day one.

Access and tools
  • A team-owned Anthropic account and workspace, with a service key for live use (not anyone's personal login)
  • Confirmation that Managed Agents, memory, checklists (outcomes) and schedules (deployments) are enabled
  • Python 3 with the anthropic package, and the ant command line tool
  • A place to run a small web service that has a public HTTPS address
  • A secrets vault and a small database table for records
  • An alert channel (chat or email) for the team
Content and people
  • A topic brief: focus areas, audience, angle, and off-limits topics
  • 5 to 10 trusted websites the agent may read
  • 15 to 20 past items we like, as style samples
  • Named approvers and a backup
  • The delivery destination (or manual delivery for version one)
  • A named owner for security and compliance sign-off
Start the reviews now

Security and vendor review can take longer than the build itself. Begin them in week one, in parallel with Phase 1.

1Create the locked workspace and get access

The agent works inside a locked workspace that can only reach the sites we list.

Tasks

  • Create the team workspace and a service key. Store the key in the secrets vault, never in code.
  • Create the environment with limited networking and the trusted sites list.
  • Create separate test and live workspaces if the company requires it.
import anthropic
client = anthropic.Anthropic()   # reads ANTHROPIC_API_KEY from the environment

SITES = ["news.example.com", "docs.example.com"]   # our trusted sites

env = client.beta.environments.create(
    name="content-writer-env",
    config={"type": "cloud",
            "networking": {"type": "limited", "allowed_hosts": SITES}},
)
print(env.id)    # keep this ID
Done when: the environment exists and its ID is stored with the project settings.

Tasks

  • Keep each file small. Many small files work better than one big one.

store = client.beta.memory_stores.create(

3Create the writer agent

The agent is a saved job description: which model, what instructions, which tools.

Tasks

  • Write the instructions in agent/system.md (see below).
  • Choose the model. Start with Claude Sonnet 5.5, and compare Claude Opus 5.5 during Phase 2.
  • Allow web search and page reading only for the trusted sites.
  • Leave out any tool that can deliver content. Delivery belongs to our service.
  • Save the agent ID and version.
agent = client.beta.agents.create(
    name="Content Writer",
    model="claude-sonnet-5-5",
    system=open("agent/system.md").read(),
    tools=[{
        "type": "agent_toolset_20260401",
        "default_config": {"enabled": True, "permission_policy": {"type": "auto"}},
        "configs": [
            {"name": "web_search", "enabled": True, "allowed_domains": SITES},
            {"name": "web_fetch",  "enabled": True, "allowed_domains": SITES},
        ],
    }],
)
print(agent.id, agent.version)   # keep both

What the instructions say

  • Your role: write internal content in our style. Read the memory files first.
  • Pick one topic from the brief that is not in the history.
  • Research only the allowed sites. Save each source with its link and an exact quote.
  • Write three drafts with different openings. Stay inside the length limits.
  • Save drafts.json and sources.json to /mnt/session/outputs/ in the formats below.
  • Never include confidential information, and never claim anything you cannot source.

5Write the checklist and tune quality

The checklist is how the agent knows what "good" means. A separate grader scores each draft and sends weak ones back.

Tasks

  • Write agent/rubric.md with clear, checkable rules (starter list below).
  • Start each run with the checklist and a retry limit of 3 to 4.
  • Build a 10-topic test set and rate the drafts blind against real examples.
  • Tune the style files, instructions and checklist. Compare Sonnet 5.5 with Opus 5.5.

Starter checklist

  • Three drafts that differ in opening and structure.
  • Each draft is within the length limits, and the first line is a specific claim, not a greeting.
  • Every factual claim points to an entry in the sources file with a link and an exact quote.
  • No phrases from the off-limits list. Tone and sentence length match the style guide.
  • One concrete example, number or story per draft.
  • Ends with one question or one takeaway, never both.
  • The topic does not appear in the history.

Use specific, checkable rules. "Data looks good" gives noisy results. "Each claim has a quote" works.

Done when: at least 6 of 10 test drafts are ones a reviewer would use with light edits.

6Build the review service

A small web service that connects the agent to people. It hears when a run finishes, checks it, asks the reviewer, and acts on the answer.

Tasks

  • Register a notice endpoint in the console and keep the signing secret in the vault.
  • On "run finished": read the real state, download the files, run the source check and the sensitive-data scan.
  • Send the drafts and sources to the approver through the chat tool or email.
  • On "change requested": send the note to the same open run as a new task with the same checklist.
  • On "approved": store a fingerprint of the exact text, then hand it to the delivery step.
  • Write the topic and the reviewer's edits to memory as new dated files.
  • Add a 15-minute check that lists recent runs and picks up anything missed.
# receives notices from Anthropic (verify the signature, ignore repeats)
event = client.beta.webhooks.unwrap(raw_body, headers=dict(request.headers))
if already_seen(event.id):
    return "", 204

if event.data.type == "session.status_idled":
    session = client.beta.sessions.retrieve(event.data.id)
    stop = latest_idle_stop_reason(client, session.id)   # read the newest idle event
    if stop == "end_turn":                                # the work is finished
        drafts, sources = download_outputs(session.id)
        report = check_sources(sources)                   # plain code, no AI
        send_for_review(session.id, drafts, sources, report)
        state.set(session.id, "awaiting_review")
    elif stop == "budget_reached":
        alert_team(session.id, "Run paused at its spending cap")

# the reviewer asks for a change
client.beta.sessions.events.send(
    session_id=session_id,
    events=[{"type": "user.define_outcome",
             "description": f"Revise draft {n}: {note}. Keep all other rules.",
             "rubric": {"type": "text", "content": RUBRIC}}],
)

# the reviewer approves draft n
digest = sha256(draft_text(n)).hexdigest()
state.approve(session_id, approver_id, n, digest)   # delivery only sends this exact text

The "run finished" notice also fires when a run is waiting for something else or has hit its cap, so the service always checks why the run stopped. Notices can repeat or arrive out of order, so it always trusts the run's real state over the order of messages.

7Add delivery

Delivery is the last step and is separate from the agent. Each destination is one small function.

Tasks

  • Give delivery its own permission, stored in the vault. The agent never holds it.

8Put it on a schedule

A schedule starts a run on chosen days and keeps a record of each one.

Tasks

  • Create the schedule with days, time zone, a spending cap and the same checklist.
  • Pin the agent version so a later edit does not change live behavior by surprise.
  • Run it by hand once while it is paused to test it.
  • Check the listed upcoming run times look right.
deployment = client.beta.deployments.create(

    agent={"type": "agent", "id": agent.id, "version": agent.version},

Done when: a scheduled run starts on its own and produces an item for review.

9Switch on the safety controls

Make the rules real in code and settings, not just in a document.

Tasks

  • Approver list: only named people can approve. Anyone else is ignored and logged.
  • Text fingerprint: approval is tied to the exact text. Editing the text voids it.
  • Approvals expire after 24 hours.
  • Hard limits: a maximum number of items per week and allowed delivery times.
  • Stop switch: one setting pauses the schedule and blocks delivery. Reviewers can also reply "pause".
  • Sensitive-data scan on every draft before the reviewer sees it.
  • Dry-run mode: during the trial, nothing is delivered automatically.

Clear roles

Builders, operators, approvers and deliverers are different people. The deliverer cannot edit code.

Secrets

Keys live only in the vault. The agent has none. Rotate on a schedule and whenever someone leaves the team.

Content rules

Off-limits topics approved by compliance, sources required for facts, and a note on whether items say they were AI-assisted.

Done when: each control is tested once on purpose: an unknown approver, an edited text, an expired approval, and the stop switch.

10Monitor and alert

Know quickly when something stops working, and who will act.

Tasks

  • Subscribe the notice endpoint to: run finished, run ended, scheduled run failed, schedule paused.
  • Alert on: failed run, run paused at its cap, item waiting more than 24 hours, no run record by the expected time, signature failures on notices.
  • Keep the 15-minute check as a safety net, because notices are not guaranteed to be delivered.
  • Send a weekly summary: items made, approved, skipped, cost.
  • Use the console's step-by-step viewer when investigating a run.

12Run the trial and go live

Two weeks of real runs with every item reviewed and nothing delivered automatically.

Tasks

  • Run the schedule for two weeks. The reviewer sees every draft.
  • Record every change the reviewer makes and add the lessons to memory.
  • Hold a go or no-go review against the targets.
  • Collect sign-offs: security, compliance, content owner, approver.
  • Turn on delivery to the chosen destination. Keep the approval step.

Go-live checklist

  • All targets met for two weeks
  • Every control in step 9 tested
  • Alerts tested
  • Runbook written and an owner and backup named
  • Sign-offs recorded
  • Stop switch known to everyone on the team
Done when: the review says go, and the first live item has been delivered.
