Claude Managed Agents, and a plan for a LinkedIn content writing agent

Part 1 explains what Managed Agents are in plain language. Part 2 is a plan to build the content writing agent on top of them, based on the pipeline in the Medium article you shared.

Part 1 · The explainerNo prior knowledge needed.

What are Claude Managed Agents?

An AI agent is Claude working through a job in several steps. It reads, searches, writes files, checks its own work, and keeps going until it is done. Normally you have to build the machinery around that: a loop that calls the model, a safe computer where its commands run, somewhere to keep its files, and a way to watch it.

Claude Managed Agents is Anthropic's hosted version of that machinery. You describe the agent once (which model, what instructions, which tools). Anthropic runs the loop and gives each run its own sandboxed computer. You start a run, watch what it does, and collect the files it produces.

Plain analogy

Building your own agent is like setting up an office, buying a laptop and hiring a person. Managed Agents is hiring a remote contractor who arrives with their own laptop and a written job description. You hand over a task and get the finished work back.

It launched in public beta in April 2026, so details can still change. Every call carries a beta header (the official SDK adds it for you).

The four pieces

Everything in Managed Agents comes down to four things. Learn these and the rest of the docs read easily.

/v1/agents

Agent

The job description. Model, system prompt, tools, skills. Saved and versioned. You create it once and reuse it.

/v1/environments

Environment

The template for the computer. Which packages are installed and which websites it may reach.

/v1/sessions

Session

One run. It pairs an agent with an environment and a first instruction, then keeps its own conversation and files.

event stream

Events

Everything that happens in a session, as a live feed: your messages, the agent's replies, each tool call, status changes.

How one run goes

Create the agent (once)
Model, instructions and tools are saved. You keep the agent ID. Editing the agent later creates a new version, and old runs keep the version they started with.
Create the environment (once)
Choose networking. limited blocks everything except the sites you list. unrestricted allows all.
Start a session
Reference the agent and environment. Optionally attach files, a GitHub repo or a memory store, and set a spending cap.
Send a task and watch events
You send a user.message. The agent works, and the stream shows each step. The session goes running, then idle when it needs you or is finished.
Collect the outputs
Files the agent saves in /mnt/session/outputs/ can be downloaded through the Files API.

A container is the sandboxed computer where the agent's commands and file edits actually run. The thinking happens on Anthropic's side and acts on the container through tools.

What can an agent do?

Agents act through tools. There are three kinds.

KindExamplesWho runs it
Built-in toolsetbash, read, write, edit, glob, grep, web_search, web_fetchAnthropic, in the session's container (web tools run on Anthropic's servers)
MCP serversConnections to outside services such as GitHub or AsanaAnthropic's orchestration layer, using credentials you store in a vault
Custom tools"Post to LinkedIn", "look up this customer"You. The agent asks, your code answers

Permissions

Each tool has a policy. always_allow runs it. always_ask pauses the session until your code approves or denies. auto lets the server judge each call: run it, deny it as high-risk, or pause for you. Anything that publishes or spends money should stay behind a person.

Good habit

A bare toolset turns on all eight tools, web search and fetch included. Switch off what the job does not need and list the sites it may read.

Features that matter for real work

Memory stores

Sessions forget everything when they end. A memory store is a folder of small text files that persists across runs, so the agent can remember which topics it already used.

Outcomes

You write a rubric. A separate grader scores the agent's work against it and sends back what is missing, until it passes or hits a retry limit. Good for "keep going until it is right".

Scheduled deployments

A cron schedule that starts a session on its own, such as every Tuesday and Thursday morning. Each firing is logged as a run.

Vaults

Safe storage for API keys and OAuth tokens. They are filled in when the agent makes a request, so the sandbox never holds the real secret.

Session budgets

A hard dollar cap on one session. At the cap it pauses instead of running on.

Multi-agent and skills

An agent can hand parts of a job to helper agents. Skills are reusable instruction packs, such as a house style guide.

Some of these were gated behind an access request early in the beta. Confirm your account has outcomes and memory stores before relying on them (this is Phase 1 of the plan).

Part 2 · Plan: Content writing agentRequirement 1 of the roadmap. A research-backed plan, ready for review.

Goal and scope

Goal. Twice a week, with no manual work, produce a ready-to-post LinkedIn post in the owner's voice, on a relevant and timely topic, and publish it only after a person approves it.

In scope

  • Topic selection from current news
  • Research with sources
  • Three drafts, scored against a rubric, rewritten if weak
  • Approval by message on the phone
  • Publishing to LinkedIn after approval

Out of scope for v1

  • Images and carousels
  • Replying to comments
  • Other networks (X, Instagram)
  • Company page posting (needs extra LinkedIn approval)

The content agent is the first of several agents. The existing project already has a review step over WhatsApp (Twilio) and a Python orchestrator, and we reuse both.

What the article describes, and how it maps

Limit of this research

Medium blocked automated access to the full article (HTTP 403), and the complete system is sold separately on Gumroad. The pipeline below comes from the article's public description in search results, so it may miss details. Please skim the article and tell me anything I got wrong.

The article describes a Python pipeline on a timer that picks topics from current AI news and researches them. It drafts three versions, scores each, rewrites weak ones, sends the options to Telegram for approval, then posts the chosen one with the LinkedIn API. It also argues that specific, assumption-challenging topics get more comments than "here is what I built" posts.

Where this plan differs on purpose. The article's author packages it as a script. Here the agent is a saved, versioned config, voice samples live in files and memory so the writing improves with feedback, and publishing is deterministic code a person has to trigger.

Agent behavior

  1. Read the voice guide and sample posts, then read memory for used topics and past reviewer edits.
  2. Search the allowed news sites, shortlist five topics, choose one that is new and specific.
  3. Research it and save notes with source links.
  4. Write three drafts with different hooks (contrarian, story, lesson).
  5. Score each against the rubric and rewrite until the outcome passes.
  6. Save drafts.json, then write the chosen topic to memory.

Starter rubric for the grader (to tune)

  • Opening line is under 140 characters and states a specific claim, not a greeting.
  • Total length is 900 to 1,300 characters.
  • Every factual claim has a source URL in the sources file.
  • No phrases on the banned list (for example "game-changer", "in today's fast-paced world").
  • Matches the voice guide: sentence length, person, level of formality.
  • Contains one concrete example, number or story.
  • Ends with one question or one clear takeaway, never both.
  • Topic does not repeat anything in the memory store from the last 60 days.
  • The three drafts differ in hook and structure.

Where the agent's voice comes from

Two layers. Static: a style guide plus 15 to 20 of the owner's best past posts, attached as read-only files. Learning: a memory store where the orchestrator writes the reviewer's edits and rejections after each approval, so each run starts smarter. Never store tokens or keys in memory.

Build sketch

This is a shape to confirm in Phase 1, not final code. Field names for deployment resources should be checked against the current SDK reference before running.

# one-time setup: run once, store the IDs
import anthropic
client = anthropic.Anthropic()

env = client.beta.environments.create(
    name="content-agent-env",
    config={"type": "cloud",
            "networking": {"type": "limited",
                           "allowed_hosts": ["techcrunch.com", "theverge.com"]}},  # your chosen news sites
)

memory = client.beta.memory_stores.create(
    name="content-memory",
    description="Topics already posted and the reviewer's edits to past drafts.",
)

agent = client.beta.agents.create(
    name="LinkedIn Content Writer",
    model="claude-sonnet-5-5",
    system=SYSTEM_PROMPT,                      # role, voice rules, output format
    tools=[{
        "type": "agent_toolset_20260401",
        "default_config": {"permission_policy": {"type": "auto"}},
        "configs": [
            {"name": "bash", "enabled": False},
            {"name": "web_search", "enabled": True,
             "allowed_domains": ["techcrunch.com", "theverge.com"]},
            {"name": "web_fetch", "enabled": True,
             "allowed_domains": ["techcrunch.com", "theverge.com"]},
        ],
    }],
)

# schedule: each firing starts a session with an outcome
deployment = client.beta.deployments.create(
    name="LinkedIn posts Tue/Thu",
    agent=agent.id,
    environment_id=env.id,
    initial_events=[{
        "type": "user.define_outcome",
        "description": "Pick today's best topic and produce three LinkedIn drafts "
                       "with sources, saved to /mnt/session/outputs/drafts.json.",
        "rubric": {"type": "text", "content": RUBRIC_MD},
        "max_iterations": 4,
    }],
    schedule={"type": "cron", "expression": "0 7 * * 2,4",
              "timezone": "<your timezone>"},
)

After each run, the orchestrator reads the deployment's runs, downloads the session outputs, sends the drafts for approval, and publishes the chosen one. The agent itself never touches the LinkedIn credentials.

Where it lives in this repo

  • agents/content_agent.py: one-time setup and a function to start a manual run.
  • agents/content_review.py: sends drafts over the existing Twilio WhatsApp path and parses the reply.
  • utils/linkedin_publisher.py: OAuth token handling and the post call.
  • content/voice/: style guide and sample posts. content/rubric.md: the grader rubric.
  • requirements.txt: add anthropic. .env: add ANTHROPIC_API_KEY and LinkedIn app keys.

Phases

Effort is a rough estimate for one developer.

Phase 0 · Decisions

0.5 day

Answer the open questions below. Gather 15 to 20 past posts and the news sites to trust.

Done when: voice samples, source list and approval channel are agreed.

Phase 1 · Prove it by hand

1 day
  • Create the API key, environment and agent. Confirm access to outcomes and memory stores.
  • Start one session manually, watch it in the Console, copy a draft out.
  • Confirm the SDK field names used in the sketch above.

Done when: one session produces three drafts with sources.

Phase 2 · Voice and rubric

2 days
  • Attach voice files, write the rubric, set max_iterations.
  • Run 10 sessions. Blind-compare drafts with your real posts and tune.

Done when: you would post at least 6 of 10 with light edits.

Phase 3 · Approval loop

1.5 days
  • Download outputs after a run, send over WhatsApp, parse the reply.
  • Write approved and rejected drafts back to memory.

Done when: a reply of "2" returns the chosen text and is saved.

Phase 4 · Publish and schedule

2 days
  • Create the LinkedIn developer app, request the posting permission, add the publisher.
  • Create the scheduled deployment with a session budget and run it manually once.

Done when: an approved draft appears on the profile and the next Tuesday run fires on its own.

Phase 5 · Harden

1 day
  • Alert on failed runs, token expiry and budget pauses.
  • Track approval rate and edits for the first month.

Done when: failures reach your phone without you checking.

Risks and how the plan handles them

RiskLikelihoodMitigation
Draft states something falseHighRubric requires a source URL per claim. The reviewer sees sources next to the draft. Nothing posts without approval.
Posts sound like generic AIHighReal voice samples, banned phrase list, edit feedback stored in memory, graded on voice.
Web pages carry hidden instructionsMediumOnly listed sites are readable. The agent has no publishing keys and no shell. A person approves every post.
Same topics repeatMediumMemory of past topics, checked by the rubric.
LinkedIn token expires or permission is deniedMediumAlert before expiry. Phase 4 starts with manual copy-and-paste posting, so the agent has value even if API access takes time. Check LinkedIn's current terms and token lifetimes when building.
Cost drifts upLowSession budget on every run, retry limit on the outcome.
Beta API changesMediumPin the agent version, keep setup in files, keep the orchestrator thin.

How we will know it works

  • Approval rate: share of runs where you pick a draft. Target 60% or more by week 4.
  • Edit distance: how much you change the chosen draft. It should fall over time.
  • Rubric pass rate within the retry limit.
  • Engagement (comments and reactions) compared with your previous posts.
